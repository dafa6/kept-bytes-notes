Kept Bytes

Two notes on the parts of a generation you only miss after they are gone.

The generated image URL that expires

You generate an image, get back a URL, paste it into a doc, and move on. Three days later the doc has a broken image in it.

This catches people in a way that feels like a bug and is actually the documented behaviour of almost every hosted generation endpoint. It is worth understanding once, because the fix is trivial and the failure is expensive.

Why the URL is temporary

The provider generated a file and put it in object storage. Serving it forever means storing it forever, for every user, including the 90% of generations nobody ever looks at again. So the URL is signed and short-lived: minutes to hours, occasionally days.

Some providers return base64 bytes instead, which has the opposite property — nothing expires, but the response is large and you have to store it yourself immediately or it is gone when the process ends.

Either way the contract is the same: the provider is handing you a result, not hosting your asset.

What actually breaks

Documents and tickets. A URL pasted into a spec, a Jira ticket or a Slack thread is a time bomb. It renders during review and is broken by the time anyone implements against it.

Caches and CDNs. If your application proxies the provider URL rather than copying the bytes, your cache holds a reference to something that will 403 later. The failure appears long after the deploy that caused it.

Retries. A job that fails partway and retries against a stored URL rather than re-generating will fail differently the second time, which makes the logs confusing.

Anything a client signed off on. The single worst version: an approved image exists only as a link in an email thread. The approval is now unverifiable and the file has to be regenerated, which — without a seed — produces a different image.

The fix, which is one line of discipline

Download the bytes at generation time. Always. Before anything else happens.

Not "when we need it", not "if the user saves it". The moment the response comes back, write the file somewhere you control and record your own URL alongside the provider's. Everything downstream references yours.

Two things to store with it, because they cost nothing now and are unobtainable later:

  • The generation parameters — model, tier, delivered size, prompt, reference count. Without these the file is an orphan and nobody can explain where it came from.
  • The original provider URL and the time you fetched it. Useful exactly once, when something does not add up and you need to establish what came from where.

The part people get wrong in the other direction

Storing everything forever is also a mistake, just a slower one. Generation is cheap enough now that the volume is real, and most of it is drafts nobody will look at again.

A workable default: keep everything for a short window, keep anything a human explicitly acted on indefinitely, and make "acted on" an event your system records rather than something you infer later. Downloaded, shared, approved, published — any of those flips the retention flag.

For people not building a pipeline

If you are generating a handful of images by hand, the whole thing reduces to one habit: save the file when you make it, not when you need it. And prefer a tool that gives you the file rather than a link with a clock on it.

It also matters whether the provenance metadata survives the round trip. A file that left the provider carrying content credentials and arrived in your folder without them has lost something you cannot re-attach, and most resize and re-encode steps strip it silently.

If you want to test the round trip before wiring anything up, you can run one on a free account and keep the file — which is also the fastest way to check what metadata your own pipeline preserves. The reasoning behind printing generation parameters next to every result, rather than leaving them to be reconstructed, is in GPT Image 2.5 Image Generator.
